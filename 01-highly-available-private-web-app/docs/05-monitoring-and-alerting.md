# Monitoring and Alerting

## Overview

Amazon CloudWatch and Amazon SNS were used to monitor the application infrastructure and send email notifications when operational thresholds were crossed.

The monitoring solution covered:

* EC2 CPU utilization
* Load balancer request count
* Application response time
* Healthy and unhealthy targets
* HTTP success and failure responses
* Alarm notifications

## Monitoring Flow

```text
AWS Resource
    ↓
CloudWatch Metric
    ↓
CloudWatch Alarm
    ↓
SNS Topic
    ↓
Email Notification
```

## SNS Configuration

An SNS Standard topic was created:

```text
Topic name: Project1-Alerts
Protocol: Email
Subscription status: Confirmed
```

The email subscription was confirmed before attaching it to CloudWatch alarms.

An unconfirmed subscription cannot receive notifications.

## EC2 Metrics

EC2 metrics were viewed under:

```text
CloudWatch
→ Metrics
→ All metrics
→ EC2
→ By Auto Scaling Group
```

The following metrics were monitored:

| Metric              | Purpose                                    |
| ------------------- | ------------------------------------------ |
| `CPUUtilization`    | Measures EC2 processor usage               |
| `NetworkIn`         | Measures incoming network traffic          |
| `NetworkOut`        | Measures outgoing network traffic          |
| `DiskReadBytes`     | Measures data read from instance storage   |
| `DiskWriteBytes`    | Measures data written to instance storage  |
| `StatusCheckFailed` | Identifies EC2 system or instance failures |

## Application Load Balancer Metrics

Load balancer metrics were viewed under:

```text
CloudWatch
→ Metrics
→ All metrics
→ ApplicationELB
→ Per AppELB, per TG Metrics
```

The following metrics were reviewed:

| Metric                      | Statistic | Purpose                               |
| --------------------------- | --------- | ------------------------------------- |
| `RequestCount`              | Sum       | Total requests received               |
| `TargetResponseTime`        | Average   | Average application response time     |
| `HealthyHostCount`          | Minimum   | Lowest number of healthy targets      |
| `UnHealthyHostCount`        | Maximum   | Highest number of unhealthy targets   |
| `HTTPCode_Target_2XX_Count` | Sum       | Successful responses from targets     |
| `HTTPCode_Target_4XX_Count` | Sum       | Client-side request errors            |
| `HTTPCode_Target_5XX_Count` | Sum       | Application server errors             |
| `HTTPCode_ELB_5XX_Count`    | Sum       | Errors generated by the load balancer |

## High CPU Alarm

A CloudWatch alarm monitored the average CPU utilization of instances in the Auto Scaling Group.

```text
Alarm name: Project1-ASG-High-CPU
Metric namespace: AWS/EC2
Metric: CPUUtilization
Dimension: Project1-App-ASG
Statistic: Average
Period: 5 minutes
Threshold: Greater than or equal to 80%
Datapoints to alarm: 2 out of 2
SNS topic: Project1-Alerts
```

Alarm logic:

```text
Average CPU remains at or above 80%
for two consecutive five-minute periods
    ↓
Alarm changes to IN ALARM
    ↓
SNS sends an email
```

The Auto Scaling target-tracking policy used a lower target of 60%.

This allowed Auto Scaling to respond before the high CPU notification threshold was reached.

## Unhealthy Target Alarm

A second alarm monitored unhealthy targets behind the Application Load Balancer.

```text
Alarm name: Project1-ALB-Unhealthy-Host
Metric namespace: AWS/ApplicationELB
Metric: UnHealthyHostCount
Statistic: Maximum
Period: 1 minute
Threshold: Greater than or equal to 1
Datapoints to alarm: 2 out of 2
SNS topic: Project1-Alerts
```

Alarm logic:

```text
One or more targets become unhealthy
for two consecutive one-minute periods
    ↓
Alarm changes to IN ALARM
    ↓
SNS sends an email
```

## Alarm States

CloudWatch alarms use three states:

| State               | Meaning                                         |
| ------------------- | ----------------------------------------------- |
| `OK`                | The metric is within the configured threshold   |
| `IN ALARM`          | The metric crossed the configured threshold     |
| `INSUFFICIENT_DATA` | CloudWatch does not yet have enough metric data |

After resource creation, alarms may temporarily show `INSUFFICIENT_DATA`.

This is normal until CloudWatch receives enough datapoints.

## Validation

The monitoring setup was validated by checking:

```text
Project1-ASG-High-CPU       → OK
Project1-ALB-Unhealthy-Host → OK
```

The dashboard showed:

* Two alarms in the OK state
* Zero alarms in the alarm state
* Zero alarms with insufficient data
* CPU utilization data from the Auto Scaling Group
* Zero unhealthy application targets

## Operational Response

### High CPU response

When the CPU alarm activates:

1. Review `CPUUtilization`.
2. Check whether Auto Scaling added instances.
3. Review `RequestCount`.
4. Review `TargetResponseTime`.
5. Check Nginx and system logs.
6. Identify whether the traffic is legitimate.
7. Check application processes consuming CPU.
8. Verify that new instances became healthy.

### Unhealthy target response

When the unhealthy-target alarm activates:

1. Open the target group.
2. Review the target health reason.
3. Confirm that Nginx is running.
4. Test `curl http://localhost`.
5. Check the application Security Group.
6. Check the health-check path and port.
7. Review EC2 status checks.
8. Confirm Auto Scaling replacement activity.

## Monitoring Limitations

The project used default EC2 and load balancer metrics.

The following were not fully configured:

* EC2 memory utilization
* EC2 filesystem utilization
* Nginx access logs in CloudWatch Logs
* Nginx error logs in CloudWatch Logs
* Application-specific custom metrics
* Distributed tracing
* CloudWatch dashboards
* VPC Flow Logs

## Production Improvements

For production environments:

* Install and configure the CloudWatch Agent
* Monitor memory and filesystem utilization
* Send Nginx access and error logs to CloudWatch Logs
* Create a centralized CloudWatch dashboard
* Configure log-retention periods
* Add alarms for target response time
* Add alarms for HTTP 5XX responses
* Add alarms for low healthy-host count
* Add NAT Gateway error and traffic monitoring
* Monitor Transit Gateway traffic
* Add CloudWatch Synthetics canaries
* Integrate alarms with incident-management tools
* Define operational runbooks for every alarm
* Use anomaly detection for dynamic workloads

## Outcome

The monitoring configuration provided visibility into application health, infrastructure utilization, traffic, and target availability.

CloudWatch alarms and SNS notifications ensured that operational issues could be detected and communicated automatically.
